    Field guide · v0.1
    
              
    Everything Hunkyard does, and how to drive it.
    
              
    
                Hunkyard is a local-first AI code reviewer for Git. It freezes a snapshot of your changes, runs a crew of
                specialist reviewers over it on the model you choose, and opens a browser workspace where you triage what
                they found, talk it through and approve fixes. This guide walks through all of it, end to end.
              
    
              
    16 chapters · about 20 minutes · / to filter
    
              
      
                
    1. 1SnapshotYour changes, frozen read-only.
      2. 
                
    2. 2CrewSpecialist reviewers on your model.
      3. 
                
    3. 3FindingsAnchored to lines, with evidence.
      4. 
                
    4. 4DecisionsAccept, dismiss, discuss.
      5. 
                
    5. 5FixesApplied only when you approve.
      6. 
              
    
            
    

            
            
    
              
    01
    
              
    Install
    
              
    You need three things:
    
              
      
                
    • Node.js 22.22 or later. Hunkyard stores history with Node's built-in SQLite. An experimental-feature warning on start is expected.
      • 
                
    • Git. Hunkyard reads your repository with your own Git install.
      • 
                
    • A model. A local runtime such as Ollama, LM Studio or llama.cpp, or an API key for a hosted provider.
      • 
              
    
              
    Install the CLI globally from npm:
    
              
    npm install --global @hunkyard/cli
    
              
    Or try it once without installing:
    
              
    npx @hunkyard/cli
    
              
    Check that everything is in place. doctor validates your configuration and asks your model runtime whether the configured model exists. Add --no-probe to skip that request and work fully offline.
    
              
    hunkyard doctor
    
              
    Hunkyard does not download models or start runtimes for you. Install and run them yourself, then point Hunkyard at them.
    
              
            
    

            
            
    
              
    02
    
              
    Your first review
    
              
    From zero to triaged findings in four steps. Run every command from inside the Git repository you want to review, or pass --repo /path/to/repo.
    
              
      
                
    1. 
                  
      Point Hunkyard at a model
      
                  
      With Ollama running and a coding model pulled:
      
                  
      hunkyard config --provider ollama --endpoint http://127.0.0.1:11434 --model qwen2.5-coder:7b --privacy local-only
      
                
      2. 
                
    2. 
                  
      Stage something
      
                  
      Stage the changes you want reviewed. Partial staging works: Hunkyard reviews exactly what is in the index, hunk by hunk.
      
                  
      git add -p
      
                
      3. 
                
    3. 
                  
      Open the workspace
      
                  
      This starts a local server on 127.0.0.1:4317 and opens your browser. It does not start a review or touch your files.
      
                  
      hunkyard
      
                
      4. 
                
    4. 
                  
      Run the review
      
                  
      The launcher reads like a sentence: Review staged changes with the standard crew on qwen2.5-coder:7b. Click any underlined word to change it. Before you run, it shows exactly where your code will go. Then press Run review.
      
                
      5. 
              
    
              
    Prefer the terminal? The same review runs without the browser and prints findings with a session ID you can open later:
    
              
    hunkyard review --staged --profile standard
    
              
    Keep the terminal open while you use the workspace. Ctrl C stops the server and cancels active work.
    
            
    

            
            
    
              
    03
    
              
    Models and providers
    
              
    Hunkyard talks to models over HTTP. Local runtimes are the default; hosted providers are available behind explicit consent.
    
              
    On your machine
    
              
    
                
    
                  
    ProviderFlagDefault endpoint
    
                  
                    
    Ollamaollamahttp://127.0.0.1:11434
    
                    
    LM Studiolm-studiohttp://127.0.0.1:1234/v1
    
                    
    llama.cpp serverllama-cpphttp://127.0.0.1:8080/v1
    
                    
    Any OpenAI-compatible servercompatiblehttp://127.0.0.1:8080/v1
    
                      
                
    
              
    
              
    hunkyard config --provider lm-studio --endpoint http://127.0.0.1:1234/v1 --model YOUR_MODEL
hunkyard doctor
    
              
    Local endpoints must be a literal loopback address, 127.0.0.1 or [::1]. Hostnames, LAN addresses and redirects are refused, so a local provider can never quietly reach another machine.
    

              
    Hosted, with consent
    
              
    OpenAI, DeepSeek and AgentRouter are supported. Each needs cloud mode and consent for the current repository. Put the key in your environment (OPENAI_API_KEY, DEEPSEEK_API_KEY or AGENTROUTER_API_KEY), or store it privately from stdin:
    
              
    hunkyard config --provider openai --store-key < /private/path/key-file
hunkyard config --provider openai --model gpt-4.1-mini --privacy cloud-allowed --allow-cloud
    
              
      
                
    • Never put a key in a command argument, a repository file or a chat. --clear-key removes a stored one.
      • 
                
    • Each environment variable overrides only its own provider. An OpenAI key is never reused for another service.
      • 
                
    • AgentRouter is a gateway: it receives your selected source and forwards it upstream. Choosing a DeepSeek-like model name there does not make it a direct DeepSeek connection.
      • 
                
    • Model IDs are yours to choose. Hunkyard never substitutes or falls back to a different model.
      • 
              
    

              
    From the workspace
    
              
    Everything above is also under Model & privacy in the workspace. The browser can save a key but never reads it back. Test saved endpoint lists available models without sending any source.
    

              
    Tuning
    
              
    config also accepts --temperature, --top-p, --context-window, --max-tokens, --max-review-tokens and --max-concurrency.
    
              
    Structured output decides how reviewers return findings: --structured-output schema (JSON schema), json (JSON mode) or text. If your runtime does not support schemas, use json or text. The Test structured output button checks what a model supports with a small synthetic prompt that contains none of your source.
    
              
            
    

            
            
    
              
    04
    
              
    Privacy and local-only mode
    
              
    Hunkyard names every destination your source code will reach before a review starts. There are two privacy modes, set per repository:
    
              
    
                
    
                  
    ModeWhat can be contacted
    
                  
                    
    local-onlyLoopback addresses only. Every hosted model and GitHub request is blocked before it leaves the process.
    
                    
    cloud-allowedHosted destinations you have explicitly consented to for this repository, plus GitHub when you pass --allow-github.
    
                      
                
    
              
    
              
    The guarantees
    
              
      
                
    • No silent fallback. If your local model fails, the review fails. It never switches to the cloud.
      • 
                
    • Consent is exact. It records the hosted origin you approved. Switching provider, changing a gateway origin or routing one reviewer elsewhere fails until you consent again.
      • 
                
    • Revocable. hunkyard config --revoke-cloud clears every hosted grant for the repository. Data already sent cannot be recalled.
      • 
                
    • No telemetry. No analytics, remote search or background calls of any kind.
      • 
                
    • Redaction. Known secret patterns and private keys are redacted before anything is sent to a model. This catches common formats, not every possible secret.
      • 
              
    
              
    Preview every destination
    
              
    Run plan to see every place a review would send source to, with your current settings and options:
    
              
    hunkyard plan
    
              
    What stays on disk
    
              
    Snapshots stored locally keep the original source, secrets included. Protect your account and the .hunkyard folder. --json output and export --include-source also contain source; treat them as sensitive.
    
              
            
    

            
            
    
              
    05
    
              
    What to review
    
              
    Pick one scope per review. In the workspace it is the first underlined word in the launcher; on the command line it is a flag.
    
              
    
                
    
                  
    FlagReviews
    
                  
                    
    --stagedStaged changes against HEAD, exactly as staged
    
                    
    --unstagedWorking-tree changes not yet staged
    
                    
    --working-treeAll changes against HEAD, staged and unstaged
    
                    
    --branch mainYour branch since its merge-base with main
    
                    
    --from A --to BThe direct difference between two commits
    
                    
    --pr 123A GitHub pull request. Needs the GitHub CLI; see GitHub pull requests
    
                      
                
    
              
    
              
    Narrowing it down
    
              
      
                
    • --include-untracked adds untracked files to --unstaged or --working-tree.
      • 
                
    • --path 'src/**' limits the review to matching paths. Repeat it for several.
      • 
                
    • --rename-threshold 1–100 sets rename detection. The default is 50.
      • 
              
    
              
    The snapshot is frozen
    
              
    When a review starts, Hunkyard captures a read-only snapshot. Edits or staging after that do not change what was reviewed, and findings stay anchored to the code they were about. Hunkyard never checks out, resets, stashes, stages, commits or fetches.
    
              
    In large repositories, prefer --staged or committed scopes. Working-tree scopes scan every tracked file and are not supported in sparse checkouts.
    
            
    

            
            
    
              
    06
    
              
    Reviewers and profiles
    
              
    A review is run by a crew of specialists, each with its own brief. A profile picks the crew and a token budget.
    
              
    
                
    
                  
    ProfileReviewersToken budget
    
                  
                    
    quickCorrectness40,000
    
                    
    standard+ Security, frontend and accessibility120,000
    
                    
    deep+ Architecture and performance, testing240,000
    
                      
                
    
              
    
              
    hunkyard review --staged --profile quick
hunkyard review --staged --profile deep --verify
    
              
    Options
    
              
      
                
    • --verify adds an independent pass that confirms or rejects findings. It cannot add new ones.
      • 
                
    • --agent-model security=MODEL routes one reviewer to a different model. Repeat it for others. Routes always inherit the repository's privacy mode, so in local-only mode no route can reach a hosted model.
      • 
                
    • --agent-concurrency N runs reviewers in parallel.
      • 
                
    • --token-budget N overrides the profile's budget. --max-cost-usd N caps hosted spend; it needs per-reviewer prices in --review-options, because Hunkyard never guesses billing rates.
      • 
                
    • --retries 0–2 retries transient network failures. --priority interactive|background orders queued reviews.
      • 
              
    
              
    For advanced routing and prices, pass JSON:
    
              
    hunkyard review --staged --profile standard --review-options \
  '{"agentModels":{"security":{"provider":"lm-studio","endpoint":"http://127.0.0.1:1234","model":"YOUR_MODEL"}}}'
    
              
    A review with no findings is a valid result, not proof that the code has no defects.
    
            
    

            
            
    
              
    07
    
              
    The workspace
    
              
    Run hunkyard in a repository to open it. Each review becomes a board: a canvas with the snapshot, the crew, the findings and their evidence laid out and connected, the way the review on this page is.

      • 
                
    • Diff editor. Open any changed file side by side or unified, with finding markers on their lines. Press Alt F1 inside the editor for accessibility help.
      • 
                
    • Context. Every run shows the related code and the rules it used, plus files left out and why: binary, very large, LFS or excluded.
      • 
                
    • Command palette. ⌘ K searches reviews and commands.

    Server and access
    
              
      
                
    • --port 4318 uses another port.
      • 
                
    • --no-browser prints a temporary access token instead of opening a browser. Don't share that output.
      • 
                
    • The token is handed to the browser once and kept only in memory, so reloading the page means reconnecting.
      • 
                
    • Only one Hunkyard process can write to a repository at a time. Stop the workspace before running a review from the CLI. Read-only commands such as sessions, doctor, storage and export can run alongside it.

    08
    
              
    Triage and discussion
    
              
    Every finding is anchored to lines in the snapshot and carries its evidence: the reviewer that raised it, the model and run that produced it, and the project rule it relied on, if any. Hunkyard validates model output against the snapshot, so a finding cannot point at code that isn't there.
    
              
    Statuses
    
              
    Each finding is open, investigating, accepted (will fix), fixed or dismissed. Filter by severity or search to focus. Every decision is recorded with the finding.
    
              
    Dismissing
    
              
    A dismissal needs a reason, so your history means something later:
    
              
      
                
    1. 1 False positive
      2. 
                
    2. 2 Preference
      3. 
                
    3. 3 Accepted risk
      4. 
                
    4. 4 Duplicate
      5. 
                
    5. 5 Out of scope
      6. 
              
    
              
    Threads
    
              
    Each session and each finding has a conversation thread. Save notes, reply, or ask the configured model a follow-up question; ⌘ Enter sends. Threads stay linked to the original run and snapshot, so they remain accurate after the code moves on.
    
              
    Learned rules
    
              
    Dismiss two findings as preference and choose Suggest a rule from my dismissals. Hunkyard drafts a session rule so the crew stops flagging that pattern. It applies only after you accept it, and your repository's rule files are never changed.
    
              
            
    

            
            
    
              
    09
    
              
    Applying fixes
    
              
    Under Propose and approve a file fix, edit a changed file yourself or ask the model for a draft. Hunkyard shows the exact change before anything is written. Then choose where it goes:
    
              
    
                
    
                  
    Apply to your working file
    
                  
    Allowed only if the file still matches the reviewed snapshot byte for byte. If you have edited it since, the fix is refused: no fuzzy merge, no staging, no forced overwrite.
    
                  
    A backup is saved as <file>.hunkyard-<id>.bak. Backups can contain secrets, so remove them once you've checked the result.
    
                
    
                
    
                  
    Try it in an isolated worktree
    
                  
    Hunkyard creates a detached worktree under .hunkyard/experiments/<id> and leaves your files alone. Test it there, then remove it:
    
                  
    git worktree remove <path>
    
                
    
              
    
              
    Each approval applies once. If the file changed after the preview, create a fresh preview and approve that exact content. Hunkyard never runs your tests, commits or pushes.
    
            
    

            
            
    
              
    10
    
              
    Project rules
    
              
    Hunkyard reads the instructions you have already written for other tools, and tells you which ones each finding relied on.
    
              
    
                
    
                  
    FileSource keyApplies to
    
                  
                    
    AGENTS.mdagentsIts folder and below; root and nested
    
                    
    CLAUDE.mdclaudeIts folder and below; root and nested
    
                    
    .github/copilot-instructions.mdcopilotWhole repository
    
                    
    .cursor/rules/**/*.mdc, .mdcursorBy each rule's glob
    
                    
    .pr_agent.tomlpr-agentpr_reviewer.extra_instructions only
    
                    
    .hunkyard/review.mdhunkyardWhole repository
    
                      
                
    
              
    
              
    Precedence
    
              
    Later sources win: root files first, then nested files, then project rules, then your global rules. The workspace shows which instructions applied to each file and flags overlaps. Instructions guide the reviewers; they can never change privacy settings or grant permissions.
    
              
    Project configuration
    
              
    Add .hunkyard/config.json to tune reviews for everyone on the project:
    
              
    {
  "rules": ["Prefer actionable correctness findings with concrete evidence."],
  "exclude": ["vendor/**", "**/*.generated.ts"],
  "instructionSources": ["agents", "claude", "cursor"],
  "instructionOrder": ["CLAUDE.md", "AGENTS.md"],
  "contextBytes": 24000
}
    
              
      
                
    • rules: extra review guidance.
      • 
                
    • exclude: paths to skip. Supports *, ** and ?; a trailing / matches a folder.
      • 
                
    • instructionSources: which instruction files to read. Defaults to all six.
      • 
                
    • instructionOrder: puts the listed files last, so they take precedence.
      • 
                
    • contextBytes: how much related code to include, from 1,024 to 100,000. The default is 24,000.
      • 
              
    
              
    Related code
    
              
    Alongside the diff, each review gets related code: imports, referenced symbols and matching test files for JavaScript and TypeScript. Binary, very large, LFS and excluded files are listed with the reason they were left out.
    
              
            
    

            
            
    
              
    11
    
              
    GitHub pull requests
    
              
    Review a pull request locally, with your own model. Hunkyard uses your GitHub CLI session and never stores GitHub credentials.
    
              
      
                
    1. 
                  
      Sign in to the GitHub CLI
      
                  
      gh auth login
      
                
      2. 
                
    2. 
                  
      Allow GitHub requests
      
                  
      GitHub access needs cloud mode, even with a local model. Cloud mode on its own does not send source to a hosted model.
      
                  
      hunkyard config --privacy cloud-allowed
      
                
      3. 
                
    3. 
                  
      Review the PR
      
                  
      hunkyard pr review 123 --allow-github
hunkyard review --pr https://github.com/owner/repo/pull/123 --allow-github --profile standard
      
                
      4. 
              
    
              
    Hunkyard captures the PR's commits, diff, comments and checks into a frozen snapshot. Your files, index and refs are not changed, and saved PR sessions reopen without a network request. Only github.com is supported, and the PR must belong to the checkout's origin.
    
              
    Refreshing
    
              
    To pick up new commits on the PR, recapture it as a new revision:
    
              
    hunkyard rerun --session SESSION_ID --revision N --recapture --allow-github
    
              
    Publishing
    
              
    Select findings in the GitHub panel, check the comment preview, enable GitHub requests and choose Confirm & publish. This posts one summary comment. It doesn't approve, request changes or add inline comments, and the CLI never publishes. Existing Qodo comments and checks are shown read-only.
    
            
    

            
            
    
              
    12
    
              
    VS Code
    
              
    The companion extension runs reviews and shows their findings next to your code. It needs VS Code 1.95 or later and the Hunkyard CLI on your PATH. Build it from the repository root and install the generated .vsix with Extensions: Install from VSIX:
    
              
    pnpm package:vscode
    
              
    Commands
    
              
      
                
    • Hunkyard: Review Staged Changes shows the repository, model and privacy mode, then reviews after you confirm.
      • 
                
    • Hunkyard: Open Local Review History loads past findings. Each one opens the reviewed source in a read-only view.
      • 
                
    • Hunkyard: Clear Findings View clears what is loaded.
      • 
              
    
              
    Settings
    
              
      
                
    • hunkyard.executable: path to the CLI if it isn't on your PATH. On Windows, point it to @hunkyard/cli/cli.mjs.
      • 
                
    • hunkyard.nodeExecutable: path to Node.js on Windows.
      • 
              
    
              
    The extension never edits, stages, fixes or publishes code, and your CLI privacy settings apply. The workspace must be trusted; virtual workspaces aren't supported. Errors go to the Hunkyard output channel.
    
            
    

            
            
    
              
    13
    
              
    History and storage
    
              
    Reviews live in .hunkyard/sqlite/history.db inside the repository. Add .hunkyard/ to your .gitignore; Hunkyard does not edit it for you.
    
              
    A session can hold several runs. Each run keeps its snapshot, rules, model settings and context, so old results stay accurate after the code changes. History is kept until you delete it.
    
              
    
                
    
                  
    CommandDoes
    
                  
                    
    sessionsLists sessions and their IDs
    
                    
    rerun --session ID --revision NReviews the same snapshot again with current settings
    
                    
    rerun … --recaptureTakes a fresh capture of the same scope
    
                    
    storageShows what history is using on disk
    
                    
    export --session IDWrites a redacted diagnostic JSON; add --include-source for source
    
                    
    delete --session ID --revision NDeletes one run
    
                    
    retain --before DATE --keep-latest NPrunes old history
    
                    
    backup --file PATHWrites a consistent backup, even during a review
    
                    
    restore --file PATHRestores a backup into an empty history
    
                      
                
    
              
    
              
    If Hunkyard stops during a review, the next start marks that run as cancelled. It never resends source automatically; start a new run to retry.
    
              
    Backups
    
              
      
                
    • The destination must not exist yet. Backups include frozen source, so keep them somewhere private. Nothing is encrypted or uploaded.
      • 
                
    • Your user config and provider keys are not included; copy them separately if you need them.
      • 
                
    • To restore, stop every Hunkyard process and move the existing .hunkyard/sqlite folder aside first. Restore refuses to overwrite history.
      • 
                
    • Back up before upgrading. Older versions can't open history written by newer ones.
      •

    Advanced features
    
              
    All optional and off by default. Ordinary reviews need none of them. Run hunkyard plan first to see what each one changes.
    
              
    Local semantic context
    
              
    A local embedding model finds related code that imports and symbol references miss. Up to five matches join the usual context, within the same size limits.
    
              
    hunkyard review --staged --semantic-model YOUR_EMBEDDING_MODEL \
  --semantic-endpoint http://127.0.0.1:11434 --allow-local-embeddings
    
              
    Redacted excerpts go only to that loopback endpoint and embeddings stay in memory. If the model fails, the review fails; there is no remote fallback.
    
              
    Shared policies
    
              
    A policy file packages a profile, rules and exclusions for a team:
    
              
    {
  "version": 1,
  "name": "Team cancellation review",
  "rules": ["Check that asynchronous work stops when its owner is disposed."],
  "exclude": ["private/**"],
  "review": { "profile": "standard", "concurrency": 2, "tokenBudget": 120000 }
}
    
              
    hunkyard policy-inspect --file team-review.json
hunkyard review --staged --policy team-review.json --allow-policy
    
              
    Policies can't change privacy, model routes or credentials. A copy is saved with each review so reruns use the same policy.
    
              
    Reviewer workflows
    
              
    By default the profile decides which reviewers run. A workflow sets their order as a small graph:
    
              
    hunkyard review --staged --review-options '{"verify":true,"workflow":{"version":1,"nodes":[
  {"agent":"correctness"},
  {"agent":"security","after":["correctness"]},
  {"agent":"verifier","after":["correctness","security"]}
]}}'
    
              
      
                
    • One to six unique built-in reviewers, including at least one specialist.
      • 
                
    • No missing or circular dependencies.
      • 
                
    • A verifier comes last, depends on every specialist and needs "verify": true.
      • 
                
    • If a reviewer fails, the ones that depend on it are skipped and the run fails.
      • 
              
    
              
    Analytics and presets
    
              
    hunkyard analytics summarises your decisions per reviewer, provider and model: accepted, fixed, false positive, other dismissals and undecided. It runs locally, on demand, and outputs counts only.
    
              
    hunkyard presets --file BENCHMARK_JSON suggests a profile from a benchmark report. It never changes your settings. Benchmarks with --live send only synthetic fixture code, never yours.
    
              
    Plugins
    
              
    Declarative plugin manifests can add review guidance. Check one with hunkyard policy-lint --file MANIFEST, then pass --plugin MANIFEST. Access to related source needs --allow-plugin-context too. Executable plugins aren't supported.

    Troubleshooting
    
              
    
                The local model is unavailable
                
    Start your Ollama, LM Studio or llama.cpp server and check the exact model name with hunkyard doctor. Hunkyard never downloads a model or falls back to a hosted one.
    
              
    
              
    
                Hosted requests are refused
                
    Hosted review needs both cloud mode and consent for this repository's destination. Grant it on purpose with config --allow-cloud. GitHub consent is separate. Never work around this by disabling local-only mode for a repository that needs it.
    
              
    
              
    
                The workspace is already running, or the port is busy
                
    Close the existing server first, or use --port 4318 for an unrelated repository. Never delete SQLite files to get past a running process.
    
              
    
              
    
                The connection token expired
                
    Reopen the workspace, or use the token printed by the process that is running now. It's temporary, held in browser memory, and separate from provider keys.
    
              
    
              
    
                A large review exceeds its budget
                
    Check the coverage and omissions the run reports. Narrow the scope with --path, or raise --token-budget to what your runtime can handle.
    
              
    
              
    
                A fix is refused with a hash conflict
                
    The file changed after the preview. Create a fresh preview and approve that exact content. Hunkyard never forces or silently restages.
    
              
    
              
    
                Node can't import SQLite
                
    Use Node.js 22.22 or later. The experimental SQLite warning on start is expected.
    
              
    
              
    
                Restore refuses existing history
                
    That is intentional. Move the existing .hunkyard/sqlite folder aside, then restore. Backups also need the repository's original path.
    
              
    
              
    For support, share a redacted hunkyard export after reading it yourself. Raw exports, backups and model logs can contain source.
